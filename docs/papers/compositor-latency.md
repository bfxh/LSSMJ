# 合成器、交换链与延迟（C1 深读 7/7）

> 来源（抓取 2026-10-01，全部 200）：
> Raph Levien《The compositor is evil》`raphlinus.github.io/ui/graphics/2020/09/13/compositor-is-evil.html`；
> Raph Levien《Swapchains and frame pacing》`.../ui/graphics/gpu/2021/10/22/swapchain-frame-pacing.html`；
> Raph Levien《A crate I want: 2d graphics》`.../rust/graphics/2018/10/11/2d-graphics.html`。
> 账本：`w3a.jsonl` 的 `W3A-060..065`。

## 1. 它解决什么成本

- 问题不是"帧率不够"，而是**延迟**：多缓冲 + 合成器排队把输入到显示的链路拉长。
- 历史坐标系（作者梳理）：早期机器直写 framebuffer，"latency was very low"（`W3A-060`，Atari 2600 只有 20 bit
  "framebuffer"）；窗口 GUI 早期应用仍直写，"延迟未被严重影响"（`W3A-061`）——**合成器是后来的层次**。
- 定义句：图形性能是**吞吐 / 延迟 / 功耗**的三角权衡（`W3A-062`）。

## 2. 机制（逐条带锚）

1. **vsync 的语义**：vsync off 时扫描立即切到新帧、旧前缓冲立刻可写；vsync on 时交换推迟到当前帧扫描结束，
   **队列深度即延迟**（`W3A-063`）。
2. **现代栈的偏置**：作者明言现代图形栈由 3D/游戏需求驱动，UI 的延迟诉求容易被牺牲（framepacing 正文）。
3. **换渲染器的成本账**（选型旁证）：自建 → 跨平台一致、测试负担低（`W3A-065`）；
   用系统库 → 构建体积/依赖重（Skia 克隆 349MB，`W3A-064`）。

## 3. 对本项目的取舍

- **吸收（判据层面）**：
  1. 验收不只看帧率，**延迟与 CPU 占用同样入账**（`W3A-062`）——GPU 档验收表增两列；
  2. present 策略**优先低延迟**：宁可 tearing-free 双缓冲，也不要深队列（`W3A-063`）；
  3. 减少层数：直贴路径（青简 Windows 侧 `UpdateLayeredWindow`，`w5a` W5A-093/094）与本条"少一层合成"同向（`W3A-060/061`）。
- **有界吸收**：自建 vs 系统库的取舍表（`W3A-064/065`）作为 ADR 的输入（我们已选"自建 + 轻量件"）。
- **不吸收**：作者对合成器的历史批判不构成"取消合成器"的工程选项（平台壳不可控）；只取"延迟优先"的判据。
